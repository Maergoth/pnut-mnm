# Leaderboard upload Worker

This optional Worker adapter supports the desktop's anonymous daily leaderboard submissions without a player sign-in. Copy remains local; an accepted new-day Submit replaces that identity's previous public rows. Same-day retries keep the original accepted update. It serves JSON at `GET /health` and `POST /snapshots`. The health route checks that the Worker is running; it does not confirm that publication is available. Publishing this source change to the hosted service is separate from a desktop release.

The trial is deployed through Sites on Cloudflare Workers at [the service health endpoint](https://pnut-leaderboard-upload.maergoth.chatgpt.site/health). PNUT submits to `/snapshots` without an external sign-in. An actual desktop-client probe confirmed a new GitHub record, a duplicate retry returning the original record, and a public read; the synthetic entry was then removed. The initial submit took 1.21 seconds and its retry 0.48 seconds from the test machine. These are observed round trips, not latency guarantees.

This folder contains no credentials, and running its checks never contacts or writes to the public leaderboard. Hosted settings are maintained separately. The desktop release remains a separate review and approval step. The current host is the managed Sites runtime, not a provisioned direct Cloudflare Free account; its limits must be checked independently.

The source adapter accepts original signed snapshots and version 2 current-reading snapshots unchanged. Version 3 publishes protected personal bests for maximum HP/Mana, attributes, AC and individual resists. Its Stat Total and Resist Total are independent best complete-reading records, never sums of unrelated individual maxima. A missing complete-reading total stays unavailable even when individual records exist. Fresh Window Capture is still required; its timestamp dates the submission, rather than claiming that all best values coexisted then. Copy continues to use the current reading.

All three formats share daily IDs and cumulative checks. Optional messages remain normalized and censored before signing; the first accepted daily snapshot/message is immutable. The version 3 adapter has **not** been deployed; the existing service supports the original/version 2 formats. Version 1.0.24's strict public reader cannot refresh a file containing a version 2 or 3 row; cached entries remain available. Deploy the compatible backend and approved desktop before the first production version 3 submission.

Use a current Node.js runtime with built-in WebCrypto. No npm install is needed:

```text
node --test leaderboard_worker/test/worker.test.js
node leaderboard_worker/build.js
node leaderboard_worker/benchmark.js
```

The build produces one standard Worker ES module at `leaderboard_worker/dist/index.js`. An optional argument chooses another output path. Tests use deterministic fixtures generated by the desktop's Python model; regenerate them with `python leaderboard_worker/generate_fixtures.py` after a format change.

Local benchmarks report both processing time and CPU time for small and large histories, using fake upstream responses. They are estimates from Node, not measurements of the hosting provider's CPU allowance. Larger histories take more work; confirm the deployed service's measured limits before relying on a particular hosting tier. See the official [Cloudflare limits](https://developers.cloudflare.com/workers/platform/limits/) and [pricing](https://developers.cloudflare.com/workers/platform/pricing/) pages for current allowances.

An initial Node 25.7 Windows run measured roughly 0.5 ms median elapsed time with an empty history, 3 ms with 100 rows, 29 ms with 1,000 rows, 147 ms with 5,000 rows, and 459 ms near the 8 MiB file limit (17,026 rows). These are local processing times with fake upstream responses, excluding real network latency. CPU counters in this environment were coarse and non-monotonic across file sizes; a 500 ms busy-loop check reported only 31–46 ms CPU. The benchmark includes a calibration probe and saves raw results under `dist/`. These results **do not establish that large histories fit a 10 ms CPU tier**. The current trial must be measured on the actual host, and growing histories need another capacity review rather than an automatic paid upgrade.
